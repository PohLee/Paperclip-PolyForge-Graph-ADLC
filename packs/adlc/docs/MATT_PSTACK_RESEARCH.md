# Matt Pocock skills 与 pstack 对当前 ADLC 的补强研究

核查日期：2026-10-29。上游固定版本：[`mattpocock/skills@59db609`](https://github.com/mattpocock/skills/tree/59db609eb1e18aaf59b63284d0e52255aff0c63c)、[`cursor/plugins@1ba91fc` 的 `pstack/`](https://github.com/cursor/plugins/tree/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack)。本地比较对象是当前**未提交**的 ADLC `0.1.8` 与 Core `0.5.0` 工作树；后续修改前应以当时的工作树重新核对。本笔记只分析可借鉴之处，没有安装或执行上游插件。

## 结论

两处既有映射只说中了部分内容。[旧映射](FACTORY_BLUEPRINT_ADAPTATION.md)把 Matt 主要归于 PM/PO/分析师的需求澄清，把 pstack 主要归于 PE/LE 的开发循环；上游现在已分别扩展为**从 intake 到依赖 ticket、实施和评审的可组合技能**，以及**由主控 skill 路由的工程 playbook、真实应用验证和结构化纠错**。[Matt README](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/README.md)明确主张小而可组合，不把整个流程交给一个框架；[pstack README](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/README.md)列出其路由技能、工程技能和 Cursor 专属自动化。因此这里建议抽取机制，保持 ADLC 自有 Graph、权限和证据契约。

当前 ADLC 已有较强的**治理与证据骨架**：角色与 21 个技能由 [index.mjs](../index.mjs) 绑定；需求使用稳定 ID 和验收条件，[requirements-discovery](../skills/requirements-discovery.md) 与 [product-definition](../skills/product-definition.md) 已覆盖来源、假设、非目标、readiness、可验证性；[implementation graph](../engineering-graphs.mjs) 已按实现形态路由并对集成候选做独立评审；[verification graph](../engineering-graphs.mjs) 和 [evidence contracts](EVIDENCE_CONTRACTS.md) 要求固定候选、逐条验收矩阵、失败阻断及未验证项的人类例外；[check-execution](../skills/check-execution.md) 有宿主提供的有界检查执行。因此不能把这些上游机制统称为“ADLC 尚无需求、测试或评审”。

## 建议顺序

**P1**

1. **给 QA 一个可复用的真实应用验证配方。** 由 QA 与 LE 建立一个项目本地验证工件：启动/健康诊断/用户路径驱动/可观察副作用/证据保留/清理；针对前 3–5 个关键功能做 feature map，并在真实可用环境跑通一条。后续维护时区分文档漂移、harness 缺口和产品回归。产物作为现有 acceptance matrix 的证据，Core runner 仍由宿主选择命令与权限。[上游生成规则](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/skills/create-verification-skill/SKILL.md)、[本地证据契约](EVIDENCE_CONTRACTS.md)。
2. **补工单的依赖与就绪语义。** PM/PO 拥有 Story 到垂直 ticket 的拆分和验收，PE/LE 拥有技术依赖与集成；每 ticket 指明 blockers、独立可验证结果、候选和完成证明，宿主从 tracker 计算 frontier。现有 Graph 的阶段/角色权限不变。[上游 to-tickets](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/to-tickets/SKILL.md)、[本地 product-definition](../skills/product-definition.md)。
3. **把 intake 变为可恢复的 triage。** PO/分析师处理新 issue、外部 PR 或反馈时，先检查重复/已实现/已拒绝，缺陷先复现，给出 `needs-info` 或 `ready` 的持久 brief，并明确人类授权后的状态转换；来源仍通过 ADLC Graph 进入 discovery/defect。可以先做 tracker 中立的状态与工件契约。[上游 triage](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/triage/SKILL.md)、[agent brief](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/triage/AGENT-BRIEF.md)。
4. **将反复人工纠错落实为可执行防线。** 从 Core 介入台账选至少出现两次的错误类别；PE 先尝试结构/类型/检查，QA 用过往错误作反例，记录 gate 是否真实失败和后续行为评测。保留人类采纳权。[上游 correct](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/skills/correct/SKILL.md)、[本地适配](MCODE_STACK_ADAPTATION.md)。

**P2**

5. **让需求访谈按决策依赖推进。** 在 [requirements-discovery](../skills/requirements-discovery.md) 增加“可查事实先查、只问人类产品判断、列下一轮依赖”的简短规则；需要统一语言时才为特定产品域建 glossary，重大且难逆转的选择再写 ADR。避免把所有小改动都变成长期访谈。[上游 grilling](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/productivity/grilling/SKILL.md)、[domain-modeling](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/domain-modeling/SKILL.md)。
6. **把评审证据分轴、分级。** PE 的独立 code review 分 Standards、Spec 两份判断；可能阻断接受的 bug 要有可重跑命令、失败输出或明确未验证标记。高风险接口变更再要求“安全前提及其运行证明”，不强制每次多模型或固定数量的评审者。[Matt 双轴 review](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/code-review/SKILL.md)、[pstack blast-radius](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/skills/blast-radius/SKILL.md)、[interrogate](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/skills/interrogate/SKILL.md)。
7. **仅为高风险状态机试点形式化验证。** pstack 在竞态、重试或状态机上建议先选择一个会伤害用户且测试难覆盖的性质，标明模型边界、同步的代码版本，并故意破坏一次证明检查能红。ADLC/Core 的 Graph 与重试逻辑可作为候选，但是否值得投入需先选具体 invariant。此项不是所有项目的默认门槛。[上游规则](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/skills/create-formal-verification-skill/SKILL.md)。

## 不宜直接照搬

- Matt 的 [`to-spec`](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/to-spec/SKILL.md) 以对话综合后发布 issue，适合轻量工程流程；ADLC 已有授权的 intent、稳定 requirement/criterion ID、逐条验证和产品 gate。可吸收测试 seam 思路，不应用一篇 issue 取代版本化的已批准需求链。
- pstack 的 [`poteto-mode`](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/skills/poteto-mode/SKILL.md) 包含特定模型、Cursor subagent 与较宽泛的外部行动自主权；[`shipping`](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/skills/poteto-mode/playbooks/shipping.md) 是 PR stack 落地机制。ADLC 应保持宿主权限、人工 release-start 授权和未选择 pipeline 的边界；此时只借鉴发布流程中可验证的 PR/候选身份，不把 PR 合并等同生产发布或完整认证。[本地 release-process](../skills/release-process.md)。
- pstack [`benchmark-checklist`](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/skills/benchmark-checklist/SKILL.md) 的误差/负载/工作是否发生等检查适合性能声明时触发；不应给每次普通变更附加重复测量。其自动化包 [benny](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/README.md) 依赖 Cursor automations 与外部输入，也不代表 ADLC 当前具有生产监控或发布能力。

以上是静态源码对照；“短板”指现有文件和契约中缺少相应可操作机制，不是通过 A/B 评测证明上游方法效果更好。建议用已有 Core 行为评测对每一项小改动单变量试验，再决定是否升为默认规则。[当前评测边界](MCODE_STACK_ADAPTATION.md)。
