# Architecture baseline

Use for system architecture, implementation readiness, planning and review.

1. Read the host-selected accepted baseline and decision, or explain why the change has no system architecture impact. Keep acceptance separate from implementation status.
2. Describe boundaries and data flow. Give each invariant a stable INV-ID, rule, enforcement, proof and status. Preserve IDs on revision; explain changed rules and retire obsolete ones explicitly.
3. Submit output and artifact using `pack.policyDocuments.evidenceContracts`. CTO records acceptance, rework or human escalation.
4. Name affected invariant IDs in plans and reviews and attach proof. Complete when baseline acceptance or reviewed non-applicability is explicit and implementation status describes what exists today.
