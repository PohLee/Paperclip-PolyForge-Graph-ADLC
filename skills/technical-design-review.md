# Technical design and review

Use this for a complex or high-impact feature whose implementation crosses boundaries or needs an explicit technical choice. Small, bounded fixes follow the normal implementation route. This adapts ideas from Google's Elephant Goldfish Model; it is not a copy of its workflow or a requirement to run every reviewer on every change.

1. The Principal Engineer starts `technical-design` with the accepted requirement and feature. Read only the relevant repository areas, approved architecture baseline, product decisions and constraints. Publish one versioned `technical_design` artifact. State the problem, scope, chosen approach, alternatives and rejection reasons, affected code paths and responsibilities, failure modes and handling, verification checks, rollback, and a targeted `contextIndex` of paths to read. An index entry names the smallest useful source and why it matters; it is a navigation aid, not proof that the source was read.
2. The host starts a fresh comprehension session with the review packet and indexed sources, excluding author conversation and hidden draft context. The Lead Engineer reads the listed paths, paraphrases the approach and records gaps and `sessionRef` in a versioned `design_comprehension` artifact. A different execution ID alone is insufficient to prove fresh context; the host authenticates session isolation and source reads.
3. QA reviews the exact design version across four axes: zoom-out/reuse, comprehension, failure modes and implementation feasibility. Check likely alternatives, integration and test seams, not just prose quality. Submit one `design_audit` with a verdict and source for every axis and stable IDs for findings. Scope depth by risk and uncertainty; do not invent findings to fill a quota.
4. The CTO/CAIO accepts, requests bounded rework, or escalates. Acceptance binds the current design, comprehension and audit artifacts. Each finding gets a `design_finding_disposition` with ID, reason and current design/audit refs; a resolved finding also cites proof. Accepted risk needs an authenticated human owner. Comprehension gaps and blocked axes require rework. Preserve prior attempts and review history.
5. Implementation readiness cites the accepted design context for complex/high-impact work. A design change publishes a new version and repeats affected review. Product scope or behavior changes still use the CPO product decision path.

The host verifies external source authenticity, reviewer/session independence and that the listed files were actually read. Core validates the declared schema, artifact versions and gate bindings; it cannot establish semantic quality from text fields.
